# Open-TMS UX交互设计 Skill (UX)

## 简介

本skill用于Open-TMS项目的UX交互设计，指导UX设计师完成从需求到界面原型的完整流程。

---

## 一、触发条件

**当需要进行以下工作时，触发本skill：**

- PM分配界面设计任务
- PRD中标注"UX待设计"的功能
- 已有界面需要优化重构
- 用户提出界面改进需求

**触发信号：**
- PM发送设计任务，包含PRD文档链接
- PRD中标注"UX待设计"
- PM-Lead分配界面优化任务

## 四、执行步骤

### 步骤1：业界洞察

**目的**：充分理解业界专业资金软件的界面设计，吸收优秀实践。

**操作**：

1. 读取 `open-tms功能特性清单.md` 了解功能定位
2. 研究FIS Quantum、SAP资金管理、Murex等业界产品的界面设计
3. 分析竞品的：
   - 布局结构
   - 交互模式
   - 信息密度
   - 数据可视化方式
4. 记录关键设计亮点作为参考

**输出**：
- 在原型文档中增加"业界对标"小节
- 说明对标哪些系统、哪些设计特性

**示例**：
```
## 业界对标
| 特性 | FIS Quantum | SAP | Open-TMS设计 |
|------|------------|-----|----------|
| 菜单 | 折叠式 | 抽屉式 | 采用侧边栏hover展开 |
| 数据表格 | 高密度 | 中等密度 | 参考Quantum高密度设计 |
```

### 步骤2：读取历史摘要

**目的**：了解本模块已有设计，避免重复和冲突。

**操作**：

1. 检查是否存在历史摘要：`docs/原型/{模块}/SUMMARY.md`
2. 若存在，读取摘要内容
3. 了解：
   - 已完成哪些页面设计
   - 设计过程中遇到的问题及解决方案
   - 已有的设计决策
   - 需要优化重构的界面

**若为新模块**：
- 创建新的摘要文件
- 在PRD开头注明"本模块为新建模块"

**输出**：
- 确认是否基于已有设计优化还是全新设计

### 步骤3：读取PRD理解需求

**目的**：深入理解功能需求，确保设计满足业务场景。

**操作**：

1. 详细阅读PM提供的PRD文档
2. 识别关键用户角色和使用场景
3. 理解业务流程和操作步骤
4. 标注需要设计的页面清单

**输出**：
- 确认设计范围
- 识别设计重点和难点
- 列出需要与PM确认的问题

### 步骤4：界面原型设计

**目的**：输出符合设计规范的界面原型。

**操作**：

1. 根据PRD功能清单设计页面结构
2. 遵循 `Open-TMS界面原型与设计规范.md` 中的设计系统：
   - [ ] 配色方案
   - [ ] 字体规范
   - [ ] 间距系统
   - [ ] 组件规格
3. 设计交互流程：
   - 列表页操作流程
   - 表单页录入流程
   - 状态变化和反馈
4. 输出界面原型文档

**注意事项**：
- 布局符合企业级系统的数据密度要求
- 交互符合用户操作习惯
- 状态反馈清晰明确
- 遵循无障碍设计原则

**输出**：
- 原型文件保存到对应路径
- 文件命名格式：`M{x}-{模块名}UX原型.md`

### 步骤5：检查设计规范一致性

**目的**：确保原型符合项目总体设计规范。

**操作**：

1. 读取 `docs/原型/Open-TMS界面原型与设计规范.md`
2. 对照检查设计中的：
   - [ ] 配色是否符合规范（主色、辅色、状态色）
   - [ ] 字体字号是否符合规范
   - [ ] 间距是否符合8px网格系统
   - [ ] 按钮样式是否符合规范
   - [ ] 表格规格是否符合规范
   - [ ] 表单布局是否符合规范
   - [ ] 交互动画是否符合规范

**检查结果处理**：

| 检查结果 | 处理方式 |
|----------|----------|
| 符合规范 | 进入下一步 |
| 不符合规范，且设计不合理 | 修改设计至符合规范 |
| 不符合规范，但设计合理 | 弹出询问用户：「此设计合理，但与总体规范存在冲突，是否需要修改规范？」 |

**询问示例**：
```
⚠️ 设计规范冲突提示

您的设计中包含以下与总体规范不一致的地方：
- 按钮使用了圆形，规范要求圆角6px
- 间距使用了7px，规范要求8px倍数

您认为此设计更合理，需要：
1. 修改设计以符合规范（推荐）
2. 修改总体规范（需用户确认）
3. 两者都修改

请选择：1 / 2 / 3
```

### 步骤6：与PM确认设计

**目的**：确保设计满足业务需求。

**操作**：

1. 准备设计稿演示
2. 向PM阐述设计思路
3. 确认以下问题：
   - 功能覆盖是否完整
   - 交互流程是否顺畅
   - 状态反馈是否清晰
   - 是否满足用户使用习惯
4. 记录PM反馈并调整设计

### 步骤7：创建GitHub Project工作项

**目的**：按照团队协作规范，创建对应的Task工作项。

**操作**：

根据原型设计内容，在GitHub Projects创建工作项：

1. **Task**：前端开发任务
   ```bash
   # 创建前端开发任务
   gh issue create --title "[M{x}-UX] {页面名称}页面设计" --body "## 设计任务\n{页面列表}\n\n## 设计稿\n{设计稿链接}\n\n## 验收标准\n- [ ] 页面布局与原型一致\n- [ ] 交互行为与原型一致\n- [ ] 样式符合设计规范" --label "UX,Task"
   ```

2. **US**：用户故事（若需要）
   ```bash
   gh issue create --title "[US] {用户角色}可通过{功能}" --body "## 用户场景\n作为{角色}，我希望{功能}，以便{目的}" --label "UX,US"
   ```

**分配规则**：

| 工作项 | Label分配 | 说明 |
|--------|-----------|------|
| 界面设计任务 | UX,Task | 分配给前端开发 |
| 用户体验优化 | UX,US | 用户故事 |

### 步骤8：生成设计摘要

**目的**：记录设计过程，便于后续追溯和团队共享。

**操作**：

1. 更新模块的 `SUMMARY.md`
2. 若模块无SUMMARY.md，则创建
3. 记录内容：
   - 本次完成的页面
   - 遇到的问题及解决方案
   - 设计决策说明
   - 待确认事项

**输出**：
- 更新 `docs/原型/{模块}/SUMMARY.md`

## 五、业界优秀实践参考

### 5.1 企业级TMS界面设计原则

**1. 数据密度与可读性平衡**
- 企业级用户需要查看大量数据，界面应保持高数据密度
- 通过分组、折叠等方式组织信息，避免信息过载
- 关键数据突出显示，次要数据可折叠

**2. 操作效率优先**
- 支持键盘快捷键（Ctrl+K搜索、Enter提交等）
- 批量操作提升效率
- 默认值和常用选项置顶

**3. 状态反馈清晰**
- 每个操作都有明确的状态反馈
- 加载中、成功、失败状态分明
- 错误信息具体且有操作指引

**4. 一致性原则**
- 同类功能保持一致的交互模式
- 视觉风格统一
- 术语表述统一

**5. 容错设计**
- 操作前确认
- 支持撤销操作
- 防止误操作的二次确认

### 5.2 业界对标参考

| 系统 | 特色 | Open-TMS借鉴 |
|------|------|--------------|
| FIS Quantum | 高数据密度表格、实时监控面板 | 数据表格设计、状态标签 |
| SAP资金管理 | 清晰的层级结构、引导式操作 | 导航设计、步骤向导 |
| Murex | 强大的数据分析、灵活的视图 | 数据可视化、自定义视图 |
| Bloomberg | 信息密集、快捷键丰富 | 键盘导航、信息组织 |

### 5.3 组件设计模式

**列表页模式**
- 工具栏：搜索 + 筛选 + 操作按钮
- 表格：可配置列、排序、分页
- 底部：状态汇总、分页导航

**表单页模式**
- 分类组织：基本信息 + 扩展信息
- 分组展示：减少单页字段数量
- 即时校验：字段级错误提示

**详情页模式**
- 头部：关键信息和状态
- 主体：详细信息（可折叠分组）
- 底部：操作日志
