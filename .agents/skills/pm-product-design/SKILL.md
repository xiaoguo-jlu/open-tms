# Open-TMS 产品设计 Skill (PM)

## 简介

本skill用于Open-TMS项目的产品需求设计（PRD），指导产品经理（PM）完成从需求分析到PRD产出的完整流程。

---

## 一、触发条件

**当需要进行以下工作时，触发本skill：**

- 为新模块编写PRD
- 为已有模块新增功能编写PRD
- 用户提出新的功能需求
- 根据用户反馈优化已有功能

**触发信号：**
- PM-Lead分配设计任务
- 用户直接提出功能需求
- 产品规划中标记为待设计的特性

| 输入项 | 来源 | 说明 |
|--------|------|------|

## 三、输出规范

### 3.1 交付件输出标准

#### 3.1.1 PRD文档标准

每个PRD必须包含以下章节：

```
# {模块名称} PRD

## 一、模块概述
- 模块名称
- 功能定位
- 用户角色
- 与其他模块的关系

## 二、功能清单
### 2.1 {子功能1}
| 功能 | 说明 | 优先级 |
|------|------|--------|
| ... | ... | P0/P1/P2 |

**字段设计**：
| 字段 | 类型 | 必填 | 说明 |

**业务流程**：
- 流程步骤说明

### 2.2 {子功能2}
...

## 三、业务规则
1. 规则1
2. 规则2

## 四、验收标准
| 功能 | 验收条件 |
|------|----------|
| ... | ... |

## 五、界面原型(UX待设计)
(简要描述或手绘示意图)

## 六、接口需求
(若涉及跨模块调用)
```

#### 3.1.2 优先级定义

| 优先级 | 定义 | 说明 |
|--------|------|------|
| P0 | 核心功能 | 必须具备，系统可用 |
| P1 | 重要功能 | 版本规划内实现 |
| P2 | 增强功能 | 可后续迭代 |

#### 3.1.3 状态定义

| 状态 | 定义 |
|------|------|
| 草稿 | 正在编写中 |
| 待评审 | 等待团队评审 |
| 已评审 | 评审通过 |
| 已冻结 | 暂停开发 |

## 四、执行步骤

### 步骤1：业界洞察

**目的**：充分理解业界专业资金软件的功能特性，确保设计具备专业性。

**操作**：

1. 读取 `open-tms功能特性清单.md`
2. 对标FIS Quantum、SAP资金管理、Murex等业界产品
3. 识别目标功能在业界的主流实现方式
4. 记录关键特性作为设计参考

**输出**：
- 在PRD中增加"业界对标"小节
- 说明对标哪些系统、哪些特性

**示例**：
```
## 业界对标
| 特性 | FIS Quantum | SAP | Open-TMS |
|------|------------|-----|----------|
| 现金池 | 支持物理池/虚拟池 | 支持 | 本版本支持虚拟池，P2支持物理池 |
| ZBA | 支持 | 支持 | P0支持 |
```

### 步骤2：读取历史摘要

**目的**：了解本模块已有设计，避免重复和冲突。

**操作**：

1. 检查是否存在历史摘要：`docs/prd/{模块}/SUMMARY.md`
2. 若存在，读取摘要内容
3. 了解：
   - 已完成哪些特性设计
   - 设计过程中遇到的问题及解决方案
   - 待确认事项
   - 已有设计决策

**若为新模块**：
- 创建新的摘要文件
- 在PRD开头注明"本模块为新建模块"

**输出**：
- 在PRD开头增加"背景"小节，说明与已有设计的关系

### 步骤3：PRD撰写

**目的**：输出符合规范的PRD文档。

**操作**：

1. 根据输出规范模板编写PRD
2. 确保包含所有必要章节
3. 功能描述清晰、无歧义
4. 验收标准明确、可测试
5. 字段定义完整

**注意事项**：
- 字段命名遵循 `Open-TMS开发规范文档.md` 中的命名规范
- 业务规则需明确无歧义
- 验收标准需可量化、可测试
- 涉及其他模块的功能，需注明接口需求

**输出**：
- PRD文件保存到对应路径
- 文件命名格式：`{模块}-{功能名}PRD.md`

### 步骤4：检查总体设计规范

**目的**：确保PRD符合项目总体设计规范。

**操作**：

1. 读取 `docs/规范/Open-TMS开发规范文档.md`
2. 对照检查PRD中的：
   - [ ] 命名是否符合数据库规范（若涉及数据表）
   - [ ] 字段类型是否符合规范（如金额用DECIMAL）
   - [ ] 编码规范是否符合（如状态字段用CHAR(1)）
   - [ ] 审计字段是否包含
   - [ ] 幂等设计是否考虑（若涉及交易）

**检查结果处理**：

| 检查结果 | 处理方式 |
|----------|----------|
| 符合规范 | 进入下一步 |
| 不符合规范，且PRD设计不合理 | 修改PRD至符合规范 |
| 不符合规范，但PRD设计合理 | 弹出询问用户：「此PRD设计合理，但与总体规范存在冲突，是否需要修改规范？」 |

**询问示例**：
```
⚠️ 规范冲突提示

您的PRD设计中包含以下与总体规范不一致的地方：
- 字段"余额"使用了FLOAT类型，规范要求使用DECIMAL(18,2)
- 缺少审计字段（created_by, created_at）

您认为此设计更合理，需要：
1. 修改PRD以符合规范（推荐）
2. 修改总体规范（需用户确认）
3. 两者都修改

请选择：1 / 2 / 3
```

### 步骤5：创建GitHub Project工作项

**目的**：按照团队协作规范，创建Feature、US、Task。

**操作**：

根据PRD内容，在GitHub Projects创建工作项：

1. **Feature**：整个功能需求
   ```bash
   gh issue create --title "[Feature] {功能名称}" --body "## 业务需求\n{PRD核心内容}\n\n## 验收标准\n{验收标准列表}" --label "PM,Feature"
   ```

2. **US**：用户故事（按用户角色拆分）
   ```bash
   gh issue create --title "[US] {用户角色}可{功能}" --body "## 用户场景\n作为{角色}，我希望{功能}，以便{目的}\n\n## 验收标准\n- [ ] {验收条件}" --label "PM,US"
   ```

3. **Task**：具体开发任务（按模块/层级拆分）
   ```bash
   gh issue create --title "[{模块}] {任务描述}" --body "## 任务描述\n{具体任务内容}\n\n## 验收标准\n- [ ] {验收条件}" --label "{角色},Task"
   ```

**分配规则**：

| 工作项 | Label分配 | 说明 |
|--------|-----------|------|
| Feature | PM,Feature | 整体需求 |
| US | PM,US | 用户故事 |
| 后端开发任务 | Dev,Task | 分配给开发 |
| 前端开发任务 | UX,Task | 分配给UX |
| 测试任务 | QA,Task | 分配给测试 |

**标题示例**：

| 场景 | Feature标题 | US标题 | Task标题 |
|------|-------------|--------|----------|
| 银行账户 | `[Feature] 银行账户管理` | `[US] 财务人员可新增银行账户` | `[M1-Dev] 银行账户后端API`<br>`[M1-UX] 银行账户页面设计`<br>`[M1-QA] 银行账户测试用例` |

### 步骤6：生成设计摘要

**目的**：记录设计过程，便于后续追溯和团队共享。

**操作**：

1. 更新模块的 `SUMMARY.md`
2. 若模块无SUMMARY.md，则创建
3. 记录内容：
   - 本次完成的功能
   - 遇到的问题及解决方案
   - 待确认事项

**输出**：
- 更新 `docs/prd/{模块}/SUMMARY.md`

## 六、质量标准

### 6.1 PRD质量检查点

| 检查项 | 标准 | 权重 |
|--------|------|------|
| 功能完整性 | 覆盖用户需求的100% | 20% |
| 描述清晰度 | 无歧义、易理解 | 20% |
| 验收标准明确性 | 可量化、可测试 | 20% |
| 字段定义完整性 | 必填、类型、说明齐全 | 15% |
| 业务流程正确性 | 符合业务逻辑 | 15% |
| 规范符合性 | 符合总体设计规范 | 10% |

### 6.2 量化指标

| 指标 | 目标值 | 最低值 |
|------|--------|--------|
| 验收标准覆盖率 | 100% | 90% |
| 字段定义完整率 | 100% | 95% |
| 规范符合率 | 100% | 95% |
| 描述歧义数量 | 0 | ≤2 |

### 6.3 评审通过标准

- [ ] 所有P0功能已包含在PRD中
- [ ] 验收标准可量化、可测试
- [ ] 无重大描述歧义
- [ ] 符合总体设计规范
- [ ] 已创建对应的GitHub工作项
