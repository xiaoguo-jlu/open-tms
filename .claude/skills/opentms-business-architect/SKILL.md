# Open-TMS 业务架构师 Skill (BA)

## 简介

本skill用于Open-TMS项目的业务架构设计工作，指导业务架构师完成从业务需求分析到业务架构设计的完整流程。本skill深度融合业界优秀全球资金管理系统（FIS Quantum、Murex、SAP Treasury & Risk Management、Kyriba、Bloomberg AIM）的架构思想和行业最佳实践。

---

## 一、触发条件

**触发信号：**
- 新模块/新产品的业务架构设计
- 跨模块业务流程梳理与优化
- 系统间集成方案设计
- 业务域拆分与模块边界划定
- 数据架构与数据模型设计
- 业务规则与工作流设计
- PM创建新Feature需求，需要业务架构分析
- 开发过程中发现业务模型不清晰

---

## 二、业界全球顶级TMS架构对标

| 系统 | 定位 | 核心优势 | 架构特点 |
|------|------|----------|----------|
| **FIS Quantum** | 全球最大TMS | 全功能覆盖、全球部署、银行直连生态 | 模块化单体+Cloud扩展 |
| **Murex** | 金融交易与风险管理 | 衍生品定价、风险计量、STP直通 | 统一交易平台MX.3，SOA架构 |
| **SAP TRM** | ERP深度集成 | 与SAP FI/CO原生集成 | SAP NetWeaver平台 |
| **Kyriba** | 云原生TMS | 现金流预测、SaaS多租户 | 纯云端，开放API平台 |
| **Bloomberg AIM** | 投资管理 | 市场数据、执行、OMS | 与Bloomberg终端深度集成 |

**五大核心洞察摘要**（详细分析见 `references/industry-insights.md`）：
1. **FIS Quantum 分层模式**: "以交易为中心"的数据模型 + "产品可配置"的业务架构，所有功能围绕交易生命周期展开
2. **交易生命周期模型**: 新建→审批→执行→结算→归档，状态机可配置，事件驱动自动流转
3. **Murex 产品工厂**: 不为每个产品单独编码，新产品 = 模板 + 参数配置 + 行为规则
4. **多级限额体系**: 集团→区域→公司层级，继承性 + 占用性 + 预警性
5. **银行集成连接器模式**: 每个外部系统封装独立Connector，标准接口，新增银行无侵入

## 五、执行步骤

### 步骤1：需求理解与业务上下文分析

**目的**：深入理解业务需求，建立业务全景图。

**操作**：
1. 阅读PRD/Feature需求，理解核心业务流程、用户画像、业务目标、业务约束
2. 分析业务上下文：识别业务域归属、上下游依赖、外部系统依赖、合规约束
3. 识别关键干系人：业务方、系统使用者、下游系统、监管要求

### 步骤2：业界最佳实践调研

**目的**：借鉴行业成熟方案，避免闭门造车。

**操作**：
1. 对标行业系统：FIS Quantum(设计模式)、Murex(产品参数化)、SAP TRM(ERP集成)、Kyriba(云原生)
2. 参考行业标准：ISO 20022、SWIFT MT/MX、FIX Protocol、IFRS 9、巴塞尔协议III
3. 输出设计参考：参考功能列表、借鉴的设计模式、需避免的常见陷阱

> 详细业界洞察分析见 `references/industry-insights.md`

### 步骤3：业务能力建模

**目的**：使用业务能力地图方法，系统化梳理业务能力。

**操作**：
1. **建立三级业务能力地图**: 按五层架构展开——流动性管理(现金池/预测/头寸)、交易管理(录入/审批/结算)、风险管理(敞口/估值/套保)、金融产品(存款/外汇/衍生品)、基础数据(组织/对手方/产品参数)
2. **识别能力成熟度**: 基础能力(必备) → 增强能力(差异化) → 创新能力(领先)
3. **能力热度分析**: 识别高频能力、关键路径能力、风险敏感能力

### 步骤4：业务流程设计

**目的**：设计符合行业标准的业务流程，覆盖完整交易生命周期。

**操作**：
1. **核心流程设计**(BPMN标准):
   - 交易创建: 用户录入 → 数据校验 → 预占限额 → 保存草稿
   - 交易审批: 提交审批 → 条件路由 → 多级审批 → 审批通过/拒绝
   - 结算处理: 结算指令 → 路由选择 → 银行通道 → SWIFT/API发送 → 状态更新
2. **异常流程**: 审批拒绝→退回修改、结算失败→重试/人工干预、超时→自动催办、撤销→状态回退
3. **关键控制点**: 权限校验、限额检查、合规检查、四眼原则

### 步骤5：领域模型设计（DDD）

**目的**：基于领域驱动设计，构建清晰的业务领域模型。

**操作**：
1. **识别核心域/支撑域/通用域**
2. **定义聚合与实体**:
   - **交易聚合(Transaction)**: 交易主体 + 对手方 + 产品 + 现金流实体 + 审批记录实体 + 结算指令值对象
   - **现金流聚合(Cashflow)**: 关联交易 + 现金流类型(本金/利息/费用) + 金额币种 + 起息日/到期日 + 状态
   - **产品聚合(Product)**: 产品参数实体 + 定价规则值对象 + 核算规则值对象 + 合规规则值对象
3. **定义领域事件**: TransactionCreated(触发限额占用) → TransactionSubmitted(触发审批) → TransactionApproved(触发结算) → TransactionSettled(触发账务) → TransactionRejected(触发限额释放)

### 步骤6：数据架构设计

**目的**：设计覆盖完整业务领域的数据架构。

**数据模型五层**: 主数据层(组织/对手方/银行/产品) → 交易数据层(交易/现金流/审批/结算) → 风险数据层(敞口/估值/减值/VaR) → 市场数据层(汇率曲线/利率曲线/波动率曲面) → 审计数据层(操作审计/状态变更/数据归档)

**数据生命周期**: 热数据(<30天，在线) → 温数据(30天-1年，在线可查) → 冷数据(>1年，离线归档)

**关键设计原则**:
- 金额字段统一 DECIMAL(18,2)，汇率 DECIMAL(18,8)
- 所有交易表必须含幂等键
- 审计字段(created_by/created_at/updated_by/updated_at)全表统一
- 货币代码使用 ISO 4217 标准，敏感数据加密存储

### 步骤7：模块划分与依赖管理

**目的**：合理划分业务模块，明确边界和依赖。

**三层模块架构**:
- **业务能力层**: 流动性管理 / 交易管理 / 风险管理 / 金融产品 / 报表分析 / 业务规则
- **基础能力层**: 基础数据 / 组织权限 / 工作流引擎
- **集成网关层**: 银行网关 / 市场数据 / ERP集成

**模块间通信**: 同步调用(实时查询) / 异步事件(非实时) / 共享数据(主数据统一维护) / API网关

### 步骤8：设计决策与方案评估

**目的**：基于行业经验，制定合理的设计决策。

**ADR模板**:

```markdown
# ADR-{序号}: {决策标题}

## 背景
{为什么要做这个决策}

## 方案选项
### 方案A: {选项A} — {描述、优点、缺点、成本}
### 方案B: {选项B} — {描述、优点、缺点、成本}

## 决策
{选择方案A/B}

## 理由
{决策理由，结合行业实践}

## 影响
{对当前模块/其他模块/数据架构的影响}

## 待办
- [ ] 事项1
```

**常见决策参考**:
- 一致性 vs 性能: 交易余额/限额占用 → 强一致性; 报表统计/审批历史 → 最终一致性
- 集成模式: 交易审批 → 同步; 结算发送/市场数据/审计日志 → 异步
- 版本规划: M1基础数据+交易 → M2金融产品+银行集成 → M3风险管理+报表 → M4+套保会计+预测

## 六、业务架构设计原则

### 6.1 核心设计原则

| 原则 | 说明 | 来源 |
|------|------|------|
| **以交易为中心** | 所有功能围绕交易生命周期展开 | FIS Quantum |
| **产品参数化** | 产品通过参数配置而非编码实现 | Murex MX.3 |
| **流程可配置** | 审批/结算/规则通过工作流配置 | 行业标准 |
| **数据统一** | 主数据统一管理，交易数据全局共享 | 数据治理 |
| **事件驱动** | 领域事件解耦模块间通信 | DDD + Event Sourcing |
| **银行无关** | 银行连接标准化，新增银行无侵入 | FIS Connect |
| **审计全面** | 全量操作审计，满足合规要求 | 监管要求 |
| **渐进演进** | 先核心后增强，版本迭代演进 | 敏捷架构 |

### 6.2 资金系统特有原则

1. **资金精确性**: 金额计算精确到最小货币单位，禁止浮点运算，统一DECIMAL
2. **交易可追溯**: 完整生命周期记录，状态变更必审计，异常必有告警
3. **限额实时性**: 占用/释放在交易确认/取消时实时执行，并发一致性保证
4. **合规优先**: 交易执行前完成合规检查(制裁名单/大额报告/外汇合规)

### 6.3 产品化设计思路(产品工厂模式)

产品定义参数维度：基础参数(编码/名称/类型/币种) → 期限参数(期限/金额) → 定价参数(利率基准/点差/费率) → 结算参数(交割方式/周期/通道) → 核算参数(科目映射/分录规则) → 风险参数(敞口计算/风险因子) → 合规参数(制裁检查/大额上报) → 审批参数(层级/阈值/加签)

新产品定义 = 选择产品模板 + 填写参数配置，无需编码。
