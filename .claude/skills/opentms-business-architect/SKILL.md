# Open-TMS 业务架构师 Skill (BA)

## 简介

本skill用于Open-TMS项目的业务架构设计工作，指导业务架构师完成从业务需求分析到业务架构设计的完整流程。本skill深度融合业界优秀全球资金管理系统（FIS Quantum、Murex、SAP Treasury & Risk Management、Kyriba、Bloomberg AIM）的架构思想和行业最佳实践。

---

## 一、触发条件

**当需要进行以下工作时，触发本skill：**

- 新模块/新产品的业务架构设计
- 跨模块业务流程梳理与优化
- 系统间集成方案设计
- 业务域拆分与模块边界划定
- 数据架构与数据模型设计
- 业务规则与工作流设计
- 技术方案评审（从业务视角）
- 版本规划与Roadmap制定

**触发信号：**
- PM创建新Feature需求，需要业务架构分析
- PM-Lead发起版本规划讨论
- 开发过程中发现业务模型不清晰
- 集成方案需要业务架构决策

### 2.2 关键架构洞察

#### 2.2.1 业务架构分层模式（FIS Quantum）

```
业务门户层（Workspace）
├── 工作台（Dashboard）/ 待办任务 / 预警中心
    │
业务能力层
├── 流动性管理：现金池、预测、头寸
├── 交易管理：录入、审批、执行、结算
├── 风险管理：敞口、估值、套保
├── 金融工具：存款、外汇、衍生品
├── 基础数据：主体、对手方、银行、产品
├── 业务规则：限额、审批、定价、核算
├── 报表分析：驾驶舱、报表、可视化
    │
技术能力层
├── 工作流引擎 / 规则引擎 / 计算引擎
├── 银行集成网关 / 市场数据网关
├── 审计日志 / 权限管理 / 数据归档
```

**核心洞察**: FIS Quantum >20年沉淀的核心在于 **"以交易为中心"的数据模型** 和 **"产品可配置"的业务架构**。所有功能都围绕"交易生命周期"展开，产品定义通过参数化配置而非编码实现。

#### 2.2.2 交易生命周期模型（行业标准）

```
                ┌─────────┐
                │  新建   │
                │  (Trade) │
                └────┬────┘
                     │
                     ▼
                ┌─────────┐
         ┌─────▶│  审批   │◀─────┐
         │      │(Approve)│      │
         │      └────┬────┘      │
         │           │           │
         │           ▼           │
         │      ┌─────────┐      │
         │      │  执行   │      │ 修改/撤回
         │      │(Execute)│      │
         │      └────┬────┘      │
         │           │           │
         │           ▼           │
         │      ┌─────────┐      │
         │      │  结算   │      │
         │      │(Settle) │      │
         │      └────┬────┘      │
         │           │           │
         │           ▼           │
         │      ┌─────────┐      │
         │      │  归档   │      │
         │      │(Archive)│      │
         │      └─────────┘      │
         │                       │
         └───────────────────────┘
```

**关键设计原则**:
- 每个状态转换都是业务事件（Event Sourcing思想）
- 状态机可配置（不是硬编码）
- 生命周期事件驱动后续动作（审批→执行→结算自动流转）

#### 2.2.3 产品工厂模式（Murex MX.3）

Murex的核心架构思想是 **"产品工厂"**：

```
产品工厂 (Product Factory)
│
├── 产品定义层
│   ├── 基础产品模板（存款、贷款、外汇、衍生品...）
│   ├── 产品参数（期限、利率、费用、结算规则...）
│   └── 产品行为（生命周期、现金流、估值模型...）
│
├── 产品实例化
│   ├── 参数继承与覆盖
│   ├── 验证规则绑定
│   └── 核算规则映射
│
└── 产品生命周期
    ├── 产品发布/下架
    ├── 版本管理
    └── 合规性检查
```

**核心洞察**: 不要为每个产品单独编码，而是构建产品定义框架。新产品 = 模板 + 参数配置 + 行为规则。

#### 2.2.4 多级限额体系（行业标准模式）

```
                    集团层级限额
                         │
            ┌────────────┼────────────┐
            │            │            │
        区域限额A    区域限额B    区域限额C
            │            │            │
      ┌─────┼─────┐      │      ┌─────┼─────┐
      │     │     │      │      │     │     │
    公司1  公司2  公司3   ...   公司4  公司5  公司6

限额种类：
├── 交易限额（单笔最大金额）
├── 净额限额（累计净头寸）
├── 信用限额（对手方总敞口）
├── 市场限额（VaR/敏感度）
└── 流动性限额（日终余额/最小备付）
```

**关键设计**: 限额具有继承性（子级继承父级）、占用性（交易占用实时扣除）、预警性（多级预警阈值）。

#### 2.2.5 银行集成架构模式

```
                  ┌──────────────────┐
                  │   TMS系统核心     │
                  │   (Open-TMS)     │
                  └────────┬─────────┘
                           │
       ┌───────────────────┼───────────────────┐
       │                   │                   │
       ▼                   ▼                   ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  银行连接器   │  │  市场数据连接器 │  │  ERP连接器    │
│ (Bank Conn.) │  │ (Market Conn.)│  │ (ERP Conn.)  │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       │                 │                 │
       ▼                 ▼                 ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  银行网关     │  │ Bloomberg/   │  │ SAP/Oracle/  │
│ (SWIFT/API)  │  │ Reuters等    │  │ 用友/金蝶     │
└──────────────┘  └──────────────┘  └──────────────┘
```

**关键设计**: 连接器模式（Connector Pattern）——每个外部系统的连接逻辑封装在独立的Connector中，通过标准接口与核心交互。新增银行/数据源只需开发对应的Connector。

## 五、执行步骤

### 步骤1：需求理解与业务上下文分析

**目的**：深入理解业务需求和上下文，建立业务全景图。

**操作**：

1. **阅读并理解PRD/Feature需求**
   - 核心业务流程
   - 用户画像（谁在用）
   - 业务目标（为什么要做）
   - 业务约束（不能做什么）

2. **分析业务上下文**
   - 识别业务域（属于哪个模块）
   - 识别上下游依赖
   - 识别外部系统依赖
   - 识别合规约束

3. **识别关键干系人**
   - 业务方
   - 系统使用者
   - 下游系统
   - 监管要求

**输出**：
- 业务上下文分析
- 干系人清单
- 初步业务范围

### 步骤2：业界最佳实践调研

**目的**：借鉴行业成熟方案，避免闭门造车。

**操作**：

1. **对标行业标准**
   - FIS Quantum同类功能的设计模式
   - Murex的产品参数化思路
   - SAP TRM与ERP集成的模式
   - Kyriba的云原生设计

2. **参考行业标准**
   - ISO 20022 金融报文标准
   - SWIFT MT/MX 报文类型
   - FIX Protocol 交易协议
   - IFRS 9 金融工具准则
   - 巴塞尔协议III 监管要求

3. **输出设计参考**
   - 参考的功能列表
   - 借鉴的设计模式
   - 需要避免的常见陷阱

### 步骤3：业务能力建模

**目的**：使用业务能力地图方法，系统化梳理业务能力。

**操作**：

1. **建立业务能力地图**

   一级能力          二级能力              三级能力（示例）
   ├── 流动性管理     ├── 现金池             ├── 物理池
   │                  │                     ├── 虚拟池
   │                  │                     ├── ZBA零余额
   │                  │                     └── 内部借贷
   │                  ├── 预测               ├── 短期预测
   │                  │                     ├── 中期预测
   │                  │                     └── 预测偏差分析
   │                  └── 头寸管理           ├── 银行头寸汇总
   │                                        ├── 账户监控
   │                                        └── 对账处理
   │
   ├── 交易管理       ├── 交易录入           ├── 手工录入
   │                  │                     ├── 模板交易
   │                  │                     └── 批量导入
   │                  ├── 审批流程           ├── 多级审批
   │                  │                     └── 条件审批
   │                  └── 结算处理           ├── 结算路由
   │                                        ├── 支付指令
   │                                        └── SWIFT发送
   │
   ├── 风险管理       ├── 敞口计量           ├── 交易敞口
   │                  │                     ├── 币种敞口
   │                  │                     └── 期限敞口
   │                  ├── 估值               ├── MTM盯市
   │                  │                     └── 估值调整
   │                  └── 套期保值           ├── 套保关系
   │                                        └── 有效性测试
   │
   ├── 金融产品       ├── 存款               ├── 活期/定期
   │                  ├── 外汇               ├── 即期/远期
   │                  └── 衍生品             ├── IRS/CDS
   │
   └── 基础数据       ├── 组织架构           ├── 法人主体
                      ├── 对手方             ├── 银行
                      └── 产品参数           └── 汇率/利率

2. **识别能力成熟度**
   - 基础能力（必备）
   - 增强能力（差异化）
   - 创新能力（领先）

   - 高频能力
   - 关键路径能力

### 步骤4：业务流程设计

**目的**：设计符合行业标准的业务流程，覆盖完整交易生命周期。

**操作**：

1. **核心流程设计**

   使用BPMN标准流程符号，设计以下核心流程：

   **交易创建流程**：
   ```
   用户录入 → 数据校验 → 预占限额 → 保存草稿 → [批量导入也在此]
   ```

   **交易审批流程**：
   ```
   提交审批 → 条件路由 → 一级审批 → 二级审批 → 审批通过
                                     ↓                       ↓
                               审批拒绝 → 退回修改      自动触发结算
   ```

   **结算处理流程**：
   ```
   结算指令 → 路由选择 → 银行通道 → SWIFT/API发送 → 结果回传 → 状态更新
   ```

2. **异常流程设计**
   - 审批拒绝 → 退回修改
   - 结算失败 → 重试/人工干预
   - 超时处理 → 自动催办/升级
   - 撤销交易 → 状态回退/冲销

3. **流程关键控制点**
   - 权限校验
   - 限额检查
   - 合规检查
   - 四眼原则

### 步骤5：领域模型设计（DDD）

**目的**：基于领域驱动设计方法，构建清晰的业务领域模型。

**操作**：

1. **识别核心领域**
   ```
   核心域：交易管理（核心业务流程）
   支撑域：基础数据、工作流、审计
   通用域：权限、通知、报表
   ```

2. **定义聚合与实体**

   **交易聚合（Transaction Aggregate）**：
   ```
   交易聚合根：Transaction（交易）
   ├── 交易主体信息
   ├── 交易对手方 (Counterparty)
   ├── 交易产品 (Product)
   ├── 交易现金流 (Cashflow[]) - 实体
   ├── 交易审批记录 (ApprovalRecord[]) - 实体
   ├── 交易结算指令 (SettlementInstruction) - 值对象
   └── 交易附件 (Attachment[]) - 值对象
   ```

   **现金流聚合（Cashflow Aggregate）**：
   ```
   聚合根：Cashflow（现金流）
   ├── 关联交易
   ├── 现金流类型（本金/利息/费用）
   ├── 金额与币种
   ├── 起息日/到期日
   └── 状态（待结算/已结算/失败）
   ```

   **产品聚合（Product Aggregate）**：
   ```
   聚合根：Product（产品）
   ├── 产品参数 (ProductParam[]) - 实体
   ├── 定价规则 (PricingRule) - 值对象
   ├── 核算规则 (AccountingRule[]) - 值对象
   └── 合规规则 (ComplianceRule[]) - 值对象
   ```

3. **定义领域事件**
   - `TransactionCreated` → 触发限额占用
   - `TransactionSubmitted` → 触发审批流程
   - `TransactionApproved` → 触发结算
   - `TransactionSettled` → 触发账务处理
   - `TransactionRejected` → 触发限额释放

### 步骤6：数据架构设计

**目的**：设计覆盖完整业务领域的数据架构。

**操作**：

1. **数据模型分层**
   ```
   ┌─────────────────────────────────────┐
   │         主数据层 (Master Data)        │
   │  组织、对手方、银行、产品、汇率/利率    │
   ├─────────────────────────────────────┤
   │         交易数据层 (Transactional)    │
   │  交易、现金流、审批记录、结算指令      │
   ├─────────────────────────────────────┤
   │         风险数据层 (Risk Data)        │
   │  敞口、估值、减值、VaR              │
   ├─────────────────────────────────────┤
   │         市场数据层 (Market Data)      │
   │  汇率曲线、利率曲线、波动率曲面        │
   ├─────────────────────────────────────┤
   │         审计数据层 (Audit Data)       │
   │  操作审计、状态变更、数据归档         │
   └─────────────────────────────────────┘
   ```

2. **数据生命周期管理**
   - 热数据：当前交易（在线，<30天）
   - 温数据：近期交易（在线可查，30天-1年）
   - 冷数据：历史归档（离线/压缩，>1年）

3. **关键数据设计原则**
   - 金额字段统一使用 DECIMAL(18,2)，汇率 DECIMAL(18,8)
   - 所有交易表必须包含幂等键
   - 审计字段（created_by/created_at/updated_by/updated_at）全表统一
   - 货币代码使用 ISO 4217 标准（三位字母）
   - 日期时间使用带时区的 TIMESTAMP
   - 敏感数据（账号、身份证等）加密存储

## 六、业务架构设计原则

### 6.1 核心设计原则

| 原则 | 说明 | 来源 |
|------|------|------|
| **以交易为中心** | 所有功能围绕交易生命周期展开 | FIS Quantum |
| **产品参数化** | 产品通过参数配置而非编码实现 | Murex MX.3 |
| **流程可配置** | 审批/结算/规则通过工作流配置 | 行业标准 |
| **数据统一** | 主数据统一管理，交易数据全局共享 | 数据治理最佳实践 |
| **事件驱动** | 领域事件解耦模块间通信 | DDD + Event Sourcing |
| **银行无关** | 银行连接标准化，新增银行无侵入 | FIS Connect |
| **审计全面** | 全量操作审计，满足合规要求 | 监管要求 |
| **渐进演进** | 先核心后增强，版本迭代演进 | 敏捷架构 |

### 6.2 资金系统特有原则

**1. 资金精确性**
- 金额计算必须精确到最小货币单位
- 浮点数运算严格禁止
- 多币种金额运算注意汇率换算精度
- 金额字段统一使用 DECIMAL(18,2) 或更精确

**2. 交易可追溯**
- 每笔交易完整生命周期记录
- 交易状态变更必须有审计
- 交易异常必须有告警和人工处理路径
- 交易修改必须保留原记录的完整快照

**3. 限额实时性**
- 限额占用必须在交易确认时实时扣除
- 限额释放必须在交易取消/失败时实时返还
- 多用户并发操作时的限额一致性保证
- 限额预警阈值必须可配置

**4. 合规优先**
- 交易执行前必须完成合规检查
- 制裁名单（OFAC/UN等）实时比对
- 大额交易自动报告
- 外汇交易合规性校验

### 6.3 产品化设计思路

借鉴Murex的"产品工厂"模式，构建可配置的产品体系：

```
产品定义参数维度：
│
├── 基础参数：产品编码、名称、类型、币种
├── 期限参数：最短/最长期限、最小/最大金额
├── 定价参数：利率基准、点差、费率结构
├── 结算参数：交割方式、结算周期、结算通道
├── 核算参数：科目映射、分录规则、过账时点
├── 风险参数：敞口计算规则、风险因子映射
├── 合规参数：制裁检查、大额上报、外汇合规
└── 审批参数：审批层级、金额阈值、加签规则
```

新产品定义 = 选择产品模板 + 填写参数配置，无需编码。
