# Open-TMS 审核评级体系

> 本文档详细定义审核评级标准,被 6 个审核 skill 强制遵循。

---

## 1. 总评级 (Overall Rating)

| 评级 | 符号 | 含义 | 后续动作 |
|------|------|------|---------|
| **A** | 🟢 | 无任何问题 | 直接进入下一 Phase |
| **B** | 🟢 | 仅 P2 问题(优化建议) | 直接进入下一 Phase,记录 P2 |
| **C** | 🟡 | 含 P1 问题(无 P0) | 修复 P1 → 复审 → 通过后继续 |
| **D** | 🔴 | 含 P0 问题 | 退回该 Phase 返工 → 重新产出 → 重新审核 |

---

## 2. 问题严重度 (Severity)

### 2.1 P0 — 阻塞性问题(零容忍)

**定义**:违反核心规范、破坏存量特性、引入合规风险、无法上线的关键缺陷。

**典型场景**:

| 维度 | P0 示例 |
|------|--------|
| 需求 | 缺失核心业务字段、状态机不完整、违反五层架构 |
| DB | 缺失审计字段、表命名违规、无索引、循环依赖 |
| API | 违反 REST 规范(用 PUT/DELETE)、缺失幂等键、错误码不规范 |
| 后端 | 缺失事务注解、硬编码业务规则、SQL 注入风险 |
| 前端 | 路由未注册、Token 未注入、关键功能无法使用 |
| UX | 关键流程无法完成、状态缺失(加载/空/错误) |

**处理**:必须返工,100% 修复后才能进入下一 Phase。

---

### 2.2 P1 — 重要问题(必须修复)

**定义**:影响可维护性、可测试性、可扩展性,但不阻塞上线。

**典型场景**:

| 维度 | P1 示例 |
|------|--------|
| 需求 | 业务规则配置化不完整、术语不一致 |
| DB | 索引设计不合理、约束缺失 |
| API | 错误码不规范、权限未细化 |
| 后端 | 单元测试覆盖率 < 80%、日志格式不规范 |
| 前端 | 组件未复用、命名风格不统一 |
| UX | 交互说明不完整 |

**处理**:必须修复后通过复审才能进入下一 Phase。

---

### 2.3 P2 — 优化建议(不阻塞)

**定义**:代码风格、注释、文档等可优化项。

**典型场景**:

| 维度 | P2 示例 |
|------|--------|
| 需求 | 文档格式不统一 |
| DB | 字段顺序可优化 |
| API | 响应示例可补充 |
| 后端 | 注释不全、变量命名 |
| 前端 | 样式可优化 |

**处理**:记录到 Feature Issue 的 `[待优化]` 标签,不阻塞流程。

---

## 3. 总评级计算规则

```python
def calculate_rating(findings):
    has_p0 = any(f.severity == 'P0' for f in findings)
    has_p1 = any(f.severity == 'P1' for f in findings)
    has_p2 = any(f.severity == 'P2' for f in findings)

    if has_p0:
        return 'D'  # 返工
    elif has_p1:
        return 'C'  # 必须修复后复审
    elif has_p2:
        return 'B'  # 通过,P2 记录到待优化
    else:
        return 'A'  # 完美通过
```

---

## 4. 评级与流程门禁关系

```
评级 A/B  ──▶  ✅ 通过 ──▶ 进入下一 Phase
评级 C    ──▶  🟡 复审 ──▶ 修复后再次审核 ──▶ 通过后进入下一 Phase
评级 D    ──▶  🔴 返工 ──▶ 退回 Phase N ──▶ 重新产出 ──▶ 重新审核
```

---

## 5. 一票否决条款

以下任一情况直接判 D,无论其他审核项:

- 违反 Open-TMS 模块依赖规则(形成循环依赖)
- 引入新的魔术字符串(未使用 GlobalConstants)
- 缺失审计字段(created_by/at/updated_by/at/version/deleted)
- 数据库表名不符合 `tms_{module}_t` 命名规范
- API 违反 POST 统一 update/delete 红线

---

## 6. 评级与时间投入

| 评级 | 预期修复时间 |
|------|------------|
| D | 数小时 ~ 1 天(返工) |
| C | 数小时(修复 P1) |
| B | 0(不修复) |
| A | 0 |

---

## 7. 评级与文档归档

| 评级 | 归档要求 |
|------|---------|
| A/B | 报告归档到 `docs/reviews/{feature}/`,Feature Issue 标注通过 |
| C | 报告归档,Issue 标注 "待修复",修复后补充复审结论 |
| D | 报告归档,Issue 标注 "返工",返工后重新审核 |

---

## 8. 评级统计与改进

PM-Lead 应每月统计:

- 各维度的评级分布(A/B/C/D 占比)
- 反复出现的 P0/P1 问题(识别共性短板)
- 平均修复时间

用于:
- 改进 Skill(checklist 完善)
- 改进培训(针对高频问题)
- 改进模板(模板前置规避问题)
