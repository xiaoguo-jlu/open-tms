# Open-TMS 测试执行 Skill (QA)

## 简介

本skill用于Open-TMS项目的测试执行工作，指导测试工程师完成从测试准备到缺陷跟踪的完整测试执行流程。

---

## 一、触发条件

当需要进行以下工作时触发：测试用例已设计完成需要执行、开发提交代码需要回归测试、发现缺陷需要验证修复、上线前需要验收测试、需要编写测试报告。

触发信号：Dev完成功能开发通知QA、PM-Lead分配测试执行任务、CI/CD自动触发测试、缺陷修复后需要重新验证。

---

## 二、输入要求

### 2.1 必须输入

- **测试用例文档**: QA自己或队友 — 已设计好的测试用例
- **接口文档**: Dev提供 — API接口定义
- **代码分支**: Dev提供 — 待测代码分支
- **测试环境**: Dev/OP提供 — 环境地址和账号
- **模块历史摘要**: `docs/testcase/{模块}/SUMMARY.md`

### 2.2 可选输入

- **PRD文档**: PM提供 — 功能需求说明
- **UX原型**: UX提供 — 界面原型
- **缺陷报告**: 上一轮缺陷列表
- **发布说明**: 本次变更内容

---

## 三、输出规范

### 3.1 测试报告标准

测试报告必须包含: 测试概况（时间/人员/环境/版本）、测试范围、测试结果汇总（用例执行结果 + 缺陷汇总）、测试结论（是否通过/遗留问题/风险评估）。

### 3.2 缺陷报告标准

缺陷报告必须包含: Bug编号、基本信息（标题/日期/版本/人员/严重程度/状态）、环境信息、缺陷描述（概述/复现步骤/预期结果/实际结果/错误日志）、缺陷分析（根因/影响范围/修复建议）。

### 3.3 存放路径规范

```
docs/
├── testreport/{模块}/v1.0/    # 测试报告（按版本分目录）
└── bugreport/{模块}/          # 缺陷报告
```

### 3.4 测试摘要标准

每次完成一轮测试后更新摘要，记录: 测试类型、执行结果（通过/失败/阻塞数量）、发现缺陷、回归测试、待确认事项。

---

## 四、执行步骤

### 步骤1：测试准备

1. 确认测试环境（地址可用、账号权限正常、数据库已初始化）
2. 确认待测版本（代码分支、构建版本）
3. 准备测试数据（正常/边界/异常数据）
4. 阅读测试用例（理解目的、前置条件、预期结果）

### 步骤2：功能测试执行

1. 按优先级执行: P0 → P1 → P2
2. 执行UI功能测试：进入页面 → 按步骤操作 → 验证结果 → 记录状态
3. 记录测试结果（通过/失败/阻塞），保存失败截图和错误日志

用例执行状态: `Pass`(通过，继续) / `Fail`(失败，创建缺陷单) / `Block`(阻塞，记录原因)。

状态定义详见 `references/status-definitions.md`。

### 步骤3：API接口测试执行

**前置条件**: 后端服务运行在 `http://localhost:8081`，Python 3.8+，requests库已安装。

**测试运行器**: `.agents/skills/opentms-test-execution/scripts/run_tests.py`

```bash
# 列出所有可用测试套件
python .agents/skills/opentms-test-execution/scripts/run_tests.py list

# 运行指定模块测试
python .agents/skills/opentms-test-execution/scripts/run_tests.py run basedata
python .agents/skills/opentms-test-execution/scripts/run_tests.py run ac
python .agents/skills/opentms-test-execution/scripts/run_tests.py run at

# 运行全部测试套件
python .agents/skills/opentms-test-execution/scripts/run_tests.py run all

# 查看历史报告
python .agents/skills/opentms-test-execution/scripts/run_tests.py report basedata
```

**测试套件说明**:

| 套件 | 测试范围 | 测试文件 |
|------|----------|----------|
| basedata | 币种/国家/银行/交易对手等基础数据API | scripts/test/basedata/test_all_post.py |
| ac | 实际现金流(AC) API | scripts/test/ac/test_ac_api.py |
| at | 账户转账(AT) API | scripts/test/at/test_at_api.py |
| full | 完整测试套件 | scripts/test/test_full.py |

**注意**: 正式测试必须使用 `run_tests.py` 脚本，禁止手写测试命令。手写curl仅用于快速探路验证。

完整命令速查见 `references/test-commands.md`。

### 步骤4：E2E端到端测试

识别核心业务流程（交易录入→审批→执行→结算），按场景执行（完整成功路径/异常中断路径/并发操作场景），跨模块验证（数据流转一致性/模块间接口调用/状态同步）。

### 步骤5：缺陷创建与跟踪

创建缺陷单（具体命令 > 详见 `opentms-pm-lead` 第九节）。

缺陷定级: 高（核心功能不可用）/ 中（功能有问题但可绕过）/ 低（体验问题）。

缺陷状态流转: 待修复 → 修复中 → 待验证 → 已关闭。状态定义详见 `references/status-definitions.md`。

常见缺陷模板见 `references/bug-templates.md`。

### 步骤6：回归测试

确定回归范围（直接影响/间接影响/核心流程P0用例），优先执行P0，执行相关P1，选择性执行P2。

### 步骤7：测试报告编写

汇总测试数据（用例执行数量/通过率/缺陷数量/严重程度分布），编写测试结论（是否通过/可否上线/遗留问题）。

### 步骤8：创建GitHub Project工作项

更新测试任务状态。具体命令 > 详见 `opentms-pm-lead` 第九节。

## 五、测试执行原则

### 5.1 测试优先级

| 优先级 | 覆盖要求 | 执行时机 |
|--------|----------|----------|
| P0 | 100%执行，100%通过 | 每次测试必执行 |
| P1 | >=90%执行，>=90%通过 | 正常测试执行 |
| P2 | >=80%执行，>=80%通过 | 时间允许时执行 |

### 5.2 测试通过标准

| 测试类型 | 通过标准 |
|----------|----------|
| P0用例 | 100%通过 |
| P1用例 | >=90%通过 |
| P2用例 | >=80%通过 |
| 缺陷修复 | 相关用例100%通过 |

### 5.3 测试环境要求

| 环境 | 用途 | 数据要求 |
|------|------|----------|
| 开发环境 | 日常测试 | 可反复修改 |
| 测试环境 | 集成测试 | 独立数据 |
| 预生产环境 | UAT/验收 | 生产级数据 |

### 5.4 缺陷关闭标准

- 相关测试用例100%通过
- 缺陷修复已验证
- 无遗留问题
- 代码已合并

## 六、与其他Skill的衔接

### 6.1 前置依赖: 测试用例设计（用例文档）+ 后端开发（API可用）+ 前端开发（界面可操作）

### 6.2 后续触发: 缺陷修复 → 回归测试 → 上线评审

### 6.3 协作流程: 开发完成 → 测试准备 → 功能测试 → 缺陷跟踪 → Dev修复 → 回归验证 → E2E测试 → 测试报告 → 上线评审
