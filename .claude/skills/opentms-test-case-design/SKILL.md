# Open-TMS 测试用例设计 Skill (QA)

## 简介

本skill用于Open-TMS项目的测试用例设计，指导测试工程师完成从需求分析到测试用例编写的完整流程。

---

## 一、触发条件

**当需要进行以下工作时，触发本skill：**

- PRD已评审，需要设计测试用例
- 功能开发完成，需要设计验收测试用例
- 上线前需要设计回归测试用例
- 需要评审已有测试用例

**触发信号：**
- PM-Lead分配测试设计任务
- Dev完成功能开发，通知QA准备测试
- 测试策略评审

---

## 二、输入要求

### 2.1 必须输入

| 输入项 | 来源 | 说明 |
|--------|------|------|
| PRD文档 | PM提供 | 功能需求文档 |
| API接口文档 | Dev提供 | 接口定义 |
| UX原型 | UX提供 | 界面原型 |

### 2.2 可选输入

| 输入项 | 来源 | 说明 |
|--------|------|------|
| 需求变更 | PM提供 | 需求变更说明 |
| 缺陷分析 | QA自行分析 | 历史缺陷分析 |
| 风险评估 | PM-Lead提供 | 项目风险 |

## 二、测试用例汇总
- 用例汇总表

### 3.2 测试用例分类

| 测试类型 | 说明 | 覆盖内容 |
|----------|------|----------|
| API接口测试 | 验证后端接口正确性 | CRUD、边界、异常 |
| UI功能测试 | 验证前端界面交互 | 操作、验证、状态 |
| E2E测试 | 验证完整业务流程 | 跨模块、端到端 |
| 集成测试 | 验证模块间交互 | 接口调用、数据流转 |

## 四、执行步骤

### 步骤1：读取输入理解需求

**目的**：深入理解功能和接口需求。

**操作**：

1. 阅读PRD文档，理解功能需求
2. 阅读API接口文档，理解接口定义
3. 阅读UX原型，理解界面交互
4. 识别测试范围和重点

**输出**：
- 确认测试范围
- 识别测试重点和难点
- 列出需要与PM/Dev确认的问题

### 步骤2：测试策略设计

**目的**：确定测试策略和测试方法。

**操作**：

1. **确定测试类型**
   - API接口测试：覆盖所有接口
   - UI功能测试：覆盖所有页面
   - E2E测试：覆盖核心业务流程

2. **确定测试层次**
   ```
   P0 - 核心功能（冒烟测试）
   P1 - 重要功能（完整测试）
   P2 - 增强功能（回归测试）
   ```

3. **确定测试方法**
   - 等价类划分
   - 边界值分析
   - 场景法
   - 错误推测法

4. **风险评估**
   - 识别高风险区域
   - 制定缓解措施

**输出**：
- 测试策略文档
- 风险评估报告

### 步骤3：API接口测试用例设计

**目的**：设计覆盖全面的API测试用例。

**操作**：

1. **按接口分类**
   - CRUD接口：列表、详情、新增、更新、删除
   - 业务接口：提交、审批、执行
   - 导出接口：Excel导出、PDF导出

2. **设计用例场景**
   - 正常场景：成功路径
   - 边界场景：最大值、最小值、临界值
   - 异常场景：必填校验、格式校验、业务规则校验
   - 权限场景：无权限访问

3. **用例命名规范**
   ```
   TC_{模块缩写}_{序号}
   例如：TC_CY_001（币种模块第1个用例）
   ```

**用例模板**：
```markdown
#### TC_XXX_001 {用例名称}

| 项目 | 内容 |
|------|------|
| 用例编号 | TC_XXX_001 |
| 用例名称 | {用例名称} |
| 测试类型 | API功能测试 |
| 优先级 | P0 |
| 接口 | {HTTP方法} /api/v1/{path} |

**前置条件**
1. {前置条件1}

**测试步骤**
1. {步骤1}
2. {步骤2}

**预期结果**
- 响应状态码：200
- 响应数据：{预期数据结构}
```

### 步骤4：UI功能测试用例设计

**目的**：设计覆盖全面的UI测试用例。

**操作**：

1. **按页面分类**
   - 列表页：查询、分页、排序
   - 编辑页：表单校验、保存、取消
   - 详情页：数据展示、状态显示

2. **设计用例场景**
   - 正常操作：成功保存、成功删除
   - 表单验证：必填校验、格式校验
   - 交互验证：按钮状态、提示信息
   - 边界验证：输入长度、特殊字符

3. **用例命名规范**
   ```
   UI_{模块缩写}_{序号}
   例如：UI_CY_001（币种UI第1个用例）
   ```

**用例模板**：
```markdown
#### UI_XXX_001 {用例名称}

| 项目 | 内容 |
|------|------|
| 用例编号 | UI_XXX_001 |
| 用例名称 | {用例名称} |
| 测试类型 | UI功能测试 |
| 优先级 | P0 |
| 页面路径 | /{path} |

**前置条件**
1. {前置条件1}

**测试步骤**
1. {步骤1}
2. {步骤2}

**预期结果**
- {预期结果描述}
```

### 步骤5：E2E测试用例设计

**目的**：设计覆盖核心业务流程的端到端测试用例。

**操作**：

1. **识别核心业务流程**
   - 交易录入→审批→执行→结算
   - 账户新增→账户编辑→账户删除
   - 资金调拨→调拨确认→调拨完成

2. **设计端到端场景**
   - 完整业务流程
   - 异常中断流程
   - 回归流程

3. **用例命名规范**
   ```
   E2E_{模块缩写}_{序号}
   例如：E2E_DEAL_001（交易E2E第1个用例）
   ```

### 步骤6：测试数据准备

**目的**：设计测试所需的测试数据。

**操作**：

1. **设计测试数据**
   - 正常数据：符合业务规则
   - 边界数据：最大/最小值
   - 异常数据：格式错误、必填为空

2. **测试数据模板**：
   ```
   | 字段 | 正常值 | 边界值 | 异常值 |
   |------|--------|--------|--------|
   | code | CNY | - | null |
   | amount | 1000.00 | 0.00 | -1.00 |
   ```

### 步骤7：创建GitHub Project工作项

**目的**：按照团队协作规范，创建测试任务。

**操作**：

```bash
# 创建测试执行任务
gh issue create --title "[QA] {模块}模块测试执行" --body "## 测试范围\n{测试范围}\n\n## 测试用例\n{用例数量}\n\n## 验收标准\n- [ ] P0用例100%通过\n- [ ] 无高优先级缺陷" --label "QA,Task"
```

### 步骤8：生成测试摘要

**目的**：记录测试设计过程。

**操作**：

1. 更新模块的 `SUMMARY.md`
2. 记录：
   - 本次完成的测试用例
   - 测试策略
   - 风险评估
   - 待确认事项

## 五、测试用例设计原则

### 5.1 等价类划分

**1. 有效等价类**
- 符合业务规则的数据
- 符合格式要求的数据

**2. 无效等价类**
- 超出范围的数据
- 格式错误的数据
- 为空的数据

### 5.2 边界值分析

- 等价类边界值
- 数值上溢/下溢
- 字符串长度边界

### 5.3 场景法

- 基本场景（成功路径）
- 备选场景（分支路径）
- 异常场景（错误处理）

### 5.4 优先级定义

| 优先级 | 定义 | 覆盖要求 |
|--------|------|----------|
| P0 | 核心功能 | 必须覆盖，100%通过 |
| P1 | 重要功能 | 应覆盖，通过率≥90% |
| P2 | 增强功能 | 可覆盖，通过率≥80% |
