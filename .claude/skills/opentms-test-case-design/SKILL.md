# Open-TMS 测试用例设计 Skill (QA)

## 简介

本skill用于Open-TMS项目的测试用例设计，指导测试工程师完成从需求分析到测试用例编写的完整流程。

---

## 一、触发条件

当需要进行以下工作时触发：PRD已评审需要设计测试用例、功能开发完成需要设计验收测试、上线前需要设计回归测试、评审已有测试用例。

触发信号：PM-Lead分配测试设计任务、Dev完成功能开发通知QA、测试策略评审。

---

## 二、输入要求

### 2.1 必须输入

- **PRD文档**: PM提供 — 功能需求文档
- **API接口文档**: Dev提供 — 接口定义
- **UX原型**: UX提供 — 界面原型
- **开发规范**: `docs/规范/Open-TMS开发规范文档.md`
- **模块已有测试用例**: `docs/testcase/`
- **模块历史摘要**: `docs/testcase/{模块}/SUMMARY.md`

### 2.2 可选输入

- **需求变更**: PM提供
- **缺陷分析**: 历史缺陷分析
- **风险评估**: PM-Lead提供

---

## 三、输出规范

### 3.1 交付件输出标准

测试用例文档包含: 测试范围（类型/模块/环境）、用例汇总表、详细测试用例（编号/名称/类型/优先级/前置条件/步骤/预期结果）。

完整模板见 `references/testcase-template.md`。用例编号与优先级规范见 `references/test-naming.md`。

### 3.2 测试用例分类

| 测试类型 | 说明 | 覆盖内容 |
|----------|------|----------|
| API接口测试 | 验证后端接口正确性 | CRUD、边界、异常 |
| UI功能测试 | 验证前端界面交互 | 操作、验证、状态 |
| E2E测试 | 验证完整业务流程 | 跨模块、端到端 |
| 集成测试 | 验证模块间交互 | 接口调用、数据流转 |

### 3.3 存放路径规范

```
docs/testcase/
├── api/        # API测试用例
├── ui/         # UI测试用例
├── e2e/        # E2E测试用例
└── SUMMARY.md  # 测试总摘要
```

### 3.4 测试摘要标准

每次完成后更新 `docs/testcase/{模块}/SUMMARY.md`，记录: 完成的用例数量、测试策略、风险评估、待确认事项。

---

## 四、执行步骤

### 步骤1：读取输入理解需求

阅读PRD、API接口文档、UX原型，识别测试范围和重点，列出待确认问题。

### 步骤2：测试策略设计

确定测试类型（API/UI/E2E）、测试层次（P0核心/P1重要/P2增强）、测试方法（等价类/边界值/场景法/错误推测法）、风险评估。

### 步骤3：API接口测试用例设计

按接口分类（CRUD/业务/导出），设计用例场景（正常/边界/异常/权限），用例命名 `TC_{模块缩写}_{序号}`。

用例模板见 `references/testcase-template.md`。

### 步骤4：UI功能测试用例设计

按页面分类（列表/编辑/详情），设计用例场景（正常操作/表单验证/交互验证/边界验证），用例命名 `UI_{模块缩写}_{序号}`。

用例模板见 `references/testcase-template.md`。

### 步骤5：E2E测试用例设计

识别核心业务流程（交易录入→审批→执行→结算），设计端到端场景（完整/异常中断/回归），用例命名 `E2E_{模块缩写}_{序号}`。

### 步骤6：测试数据准备

设计测试数据模板: 正常数据（符合业务规则）、边界数据（最大/最小值）、异常数据（格式错误/必填为空）。

### 步骤7：创建GitHub Project工作项

创建测试执行Task。具体命令 > 详见 `opentms-pm-lead` 第九节。

### 步骤8：生成测试摘要

更新 `docs/testcase/{模块}/SUMMARY.md`，记录完成的用例、测试策略、风险评估。

## 五、测试用例设计原则

### 5.1 等价类划分

有效等价类（符合业务规则/格式）和无效等价类（超出范围/格式错误/为空）。

### 5.2 边界值分析

等价类边界值、数值上溢/下溢、字符串长度边界。

### 5.3 场景法

基本场景（成功路径）、备选场景（分支路径）、异常场景（错误处理）。

### 5.4 优先级定义

| 优先级 | 定义 | 覆盖要求 |
|--------|------|----------|
| P0 | 核心功能 | 必须覆盖，100%通过 |
| P1 | 重要功能 | 应覆盖，>=90%通过 |
| P2 | 增强功能 | 可覆盖，>=80%通过 |

## 六、与其他Skill的衔接

### 6.1 前置依赖: 产品设计(PM) PRD + 后端开发 API + 前端开发 UI

### 6.2 后续触发: 测试用例执行 → 缺陷管理

### 6.3 协作流程: PRD/开发 → 测试用例设计 → 测试执行 → 缺陷跟踪 → Bug修复 → 回归测试

---

## 七、质量标准

### 7.1 测试用例质量检查点

| 检查项 | 标准 | 权重 |
|--------|------|------|
| 覆盖完整性 | P0用例100%覆盖 | 30% |
| 用例独立性 | 用例间无依赖 | 20% |
| 步骤清晰度 | 步骤明确可执行 | 20% |
| 预期明确性 | 预期结果可验证 | 20% |
| 文档规范性 | 格式符合规范 | 10% |

### 7.2 量化指标

| 指标 | 目标值 | 最低值 |
|------|--------|--------|
| P0覆盖率 | 100% | 100% |
| P1覆盖率 | >=90% | 80% |
| 用例执行率 | 100% | 90% |
| 缺陷报告率 | 100% | 90% |
